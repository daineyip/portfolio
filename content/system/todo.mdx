## Real email

The Inbox builds a `mailto:` and hands off to whatever mail client the visitor has.
That was the right first move — no backend, no secret, nothing to leak — but it asks
the visitor to finish the job in another app, and on a machine with no mail client
configured it does nothing at all. Worse, the address has to ship in the bundle for
the handoff to work, so it is scrapeable no matter what the window displays.

Send it properly instead:

- **Resend** is the better fit — built for transactional mail from an app, and the
  free tier covers a portfolio comfortably. Twilio SendGrid is the alternative and
  the heavier one; its API is aimed at volume this will never have
- The send goes through a route handler, not the browser, so the API key stays on
  the server and the address never reaches the bundle. `send()` in `Inbox.tsx` is
  already the only thing that would change — swap the `mailto:` for a `POST`
- Needs a honeypot field and rate limiting by IP before it goes anywhere near
  public, or it becomes someone's relay
- Keep a `mailto:` link somewhere as the fallback for when the send fails

## A chatbot that knows the desktop

An app in the OS you can ask about the work, rather than opening folders until you
find it. The interesting part isn't the chat — it's that the desktop can hand the
model everything it needs to be specific.

- **Context is already built.** `lib/search-index.ts` produces the plain text of
  every document at build time for `Cmd+K`; the same index is the system prompt. The
  tree in `data/tree.ts` tells it what exists and how it's arranged
- **Give it the desktop as tools**, not just as text: open a node, run a search,
  say which windows are open. `useOpenNode()` is already the single definition of
  what opening means, so a tool call lands the visitor in the right window rather
  than describing it. Answering "where's the Binance work?" by *opening* it is the
  whole point
- Route handler again — the API key never belongs in the browser. The
  `@anthropic-ai/sdk` package, `claude-opus-5`, streaming so the reply arrives as
  it's written
- The document text is a large, unchanging prefix on every request, which is exactly
  what prompt caching is for. Put it before anything that varies
- It renders as another `appType` with its own template, so it opens, minimizes and
  pins like every other window. That part is the easy part
- Needs a spend ceiling and rate limiting before it's public

## Dark mode

The palette already lives in `app/globals.css` as tokens — `--paper`, `--desk`,
`--accent`, `--alert`, `--ok` — so a dark theme is mostly a second set of values rather
than a rewrite. The work is in the details the tokens don't cover:

- The hard black drop shadows are the whole visual language, and black-on-dark reads as
  nothing. They need a light shadow colour, not a removed one
- The `border-[3px]` black borders have the same problem
- The wallpaper dot grid needs its own contrast pass
- Respect `prefers-color-scheme` on first visit, then let a menu-bar toggle override it
  and remember the choice
